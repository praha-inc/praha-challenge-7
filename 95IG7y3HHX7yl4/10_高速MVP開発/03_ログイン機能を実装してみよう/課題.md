### OAuth2.0
OAuth2.0は、サードパーティアプリケーションに対して、ユーザーに代わってリソースにアクセスする権限（認可）を付与するための仕組みです。
OAuth を利用することで、ユーザーはサードパーティに HTTP サービスの ユーザー名（ID）やパスワードを教える必要がなくなる。

1. Webサービス「A」が、ユーザーのGoogleカレンダーデータにアクセスしたい
2. ユーザーはGoogleにログイン済み
3. OAuth2.0により、GoogleはユーザーにWebサービス「A」へのアクセス権付与について確認
4. ユーザーが同意すれば、Webサービス「A」はアクセストークンを受け取り、カレンダーデータにアクセス可能に

## OAuth2.0の仕組みを図で説明してください。次の4つのロールについて、詳細とそれぞれの関係を説明してください。
### 1. リソースオーナー (Resource Owner)
- **定義**: 保護されたリソースへのアクセスを許可できる人やエンティティ
- **典型例**: エンドユーザー
- **役割**:
  - 自分のリソースへのアクセス権をクライアントに付与する
  - 認可サーバーで認証を行い、クライアントにアクセス権限を与えるかどうかを判断する

### 2. クライアント (Client)
- **定義**: リソースオーナーの代わりに保護されたリソースにアクセスするアプリケーション
- **典型例**: Webアプリ、モバイルアプリ、デスクトップアプリなど
- **役割**:
  - リソースオーナーの許可を得てリソースにアクセスする
  - 認可サーバーからアクセストークンを取得し、リソースサーバーにリクエストを行う

### 3. 認可サーバー (Authorization Server)
- **定義**: リソースオーナーを認証し、クライアントにアクセス権限（トークン）を発行するサーバー
- **役割**:
  - リソースオーナーの認証を行う
  - リソースオーナーの同意を確認する
  - クライアントにアクセストークンを発行する
  - 必要に応じてリフレッシュトークンも発行する

### 4. リソースサーバー (Resource Server)
- **定義**: 保護されたリソースをホストするサーバー
- **典型例**: APIサーバー
- **役割**:
  - アクセストークンを検証する
  - 有効なトークンを持つクライアントに対して保護されたリソースへのアクセスを許可する

## OAuth2.0（特に認可コードグラント）の仕組みを説明するうえで必ず登場するであろう次のワードについて、それぞれ説明してください。
- アクセストークン
クライアントからリソースサーバーへのリクエストはすべてアクセストークンをつける必要があります。そしてアクセストークンは、誰のどのリソースに対してどのような操作が許可されているかということと、有効期限に関する情報を持っています。
OAuth のアクセストークンは Bearer トークン（署名なしトークン）という仕様になっており、トークンを所持する任意のクライアントは「トークンを所持している」という条件を満たしていればトークンを利用することができます。つまり、トークン所持者についての確認は行いません。

- リフレッシュトークン
クライアントから認可サーバーに対してアクセストークンの再発行を求める際に利用します。
リフレッシュトークンの発行は標準仕様では必須ではなく、利用する API によってはリフレッシュトークンを発行する機能が提供されていないこともあります。
アクセストークンはクライアントからリソースサーバーに送るものですが、リフレッシュトークンは認可サーバーに送るものです。
有効期限は一ヶ月などの長期間になっています。

- 認可コード
リソースオーナーがクライアントへの権限移譲に同意した証として発行されます。これはクライアントから認可サーバーに対してアクセストークンを要求する際に利用されます。
認可サーバーはリソースオーナーの ユーザー名（ID） とパスワードを確認し、アクセス権限の委譲に対して同意を得ます。
認可コードは一度の発行につき一回しかアクセストークンを要求することはできません。
認可コードの有効期限は標準仕様では 10 分を推奨しています。

- 認可エンドポイント
認可サーバーによって提供されるエンドポイントで、認可コードの発行が主な役割です。
クライアントがアクセス権をもっていないリソースにアクセスするとき、まず認可エンドポイントを叩く必要があります。ここではユーザー名とパスワードの入力などによってリソースオーナーの認証を行います。認証完了後に、リソースオーナーはアクセス権限の委譲に同意します。その同意の証明として認可コードがリダイレクトエンドポイントに送られます。

- リダイレクトエンドポイント
クライアントが提供するエンドポイントで、リダイレクト URI とも呼ばれています。リダイレクト URI は認可サーバーから認可コードを受け取るために使われます。認可サーバーはリソースオーナーからのアクセス権限委譲の同意が完了すると、HTTP ステータスコード 302 を返してリダイレクト URI にリダイレクトします。その際、クエリパラメーターとして認可コードが渡されます。

- トークンエンドポイント
認可サーバーによって提供されるエンドポイントで、認可コードと必要なパラメーターを指定してトークンエンドポイントにリクエストを投げることでアクセストークンが発行されます。
トークンエンドポイントでは Basic 認証によってクライアントが認証されます。Authorization ヘッダーにクライアント ID とクライアントシークレットを設定することでクライアントを識別します。クライアント ID とクライアントシークレットは認可サーバーに事前登録する際に発行されます。

## OIDC（OpenID Connect）は、OAuth2.0をベースにした拡張仕様です。OAuth2.0が認可に特化しているのに対して、OIDCはユーザーの認証情報を提供するための仕組みを加えています。OIDCの認可コードフローについて、シーケンス図と流れの説明を書いてみてください。
> ヒント: OAuth2.0で「グラントタイプ」と呼ばれていたものはOIDCでは「フロー」と呼ばれます。（認可コードグラント→認可コードフロー）
> ヒント: 他にも、OIDCではロールの名前がOAuth2.0と若干違います。以下のマッピングで読み替えると調べやすいかもしれません。
>  - （OAuth2.0での呼び方） → （OIDCでの呼び方）
>  - リソースオーナー → エンドユーザー
>  - クライアント → リライング・パーティ
>  - 認可サーバー → IDプロバイダー
>  - リソースサーバー → UserInfoエンドポイント

### クライアントアプリに発行されるトークン

  - IDトークン: 「ユーザーが誰であるか」 を証明するためのもの。（認証）
- OIDC: IDトークン

### そもそもIDトークは必要？アクセストークンだけでは駄目なの？
そもそも、
アクセストークンは 「この人は〇〇のリソースにアクセスできる権限を持っている」という**認可**の証明
IDトークンは 「この人は確かに△△という人物である」という**認証**の証明

IDトークンは認証の証明なので、追加リクエストなしに認証情報を確認でき、シングルサインオン(SSO)やID連携の基盤となる。
